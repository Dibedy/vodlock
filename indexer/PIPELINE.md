# Canonical broadcast pipeline

## Unattended recovery

The 2026-10-11 production audit found three watch-party jobs classified as unsupported after an oversized scoreboard window, repeated obsolete alignment/validation warnings, historical metadata refresh competing with current processing, and old failed deployment verifications after the provider quota incident. Official indexes for the latest completed broadcast had already finalized; optional watch-party failures must not hold those indexes back.

Operational failures now persist `failure_kind`, `failure_count`, `recovery_count`, `wait_count`, and `recovery_at`. Network, timeout, rate-limit, temporarily unavailable-source and resource failures use exponential backoff with 20% jitter. HTTP Retry-After seconds/dates are honoured up to 24 hours. After the configured failed-attempt limit, eligible operational failures receive two recovery cycles with six-hour and twelve-hour cooldowns. A third exhausted cycle requires review. Confirmed progress resets the recovery cycle; clean shutdown requeues without consuming a failure. Missing credentials, unsupported formats and invalid data are not disguised as successful processing. Dependency waits back off independently and have a persistent fourteen-day deadline rather than remaining stuck forever. Explicit operator retry resets the recovery/dependency budget but retains useful checkpoints.

Expired leases close the abandoned attempt, classify the failure as `worker_crash`, and defer reclaim using bounded jittered backoff. Generation/lease guards still reject stale writes. Optional Twitch capture/alignment and separate-upload comparisons can run alongside official processing on different sources. Same-source work stays serialized. Alignment writes recheck source and canonical revisions, completed scoreboard checks recheck the current immutable index set, and upload comparisons use the segment revision as a compare-and-set guard.

Twitch scoreboard searches decode at most 25 seconds at a time with same-continuity-group preroll, a twelve-segment/64 MiB encoded cache, and a 128 MiB temporary chunk limit. HLS discontinuities split independent decoder inputs instead of concatenating unrelated transport clocks. Every decoder generator closes before its temporary directory is removed. Longer round searches checkpoint their actual observations after a 45-second processing slice and resume at the next sample; they do not repeatedly restart the 180-second fallback. A blocked FFmpeg pipe is killed after 45 seconds without a read returning, excluding time spent by the OCR consumer. No confidence, coverage, replay or five-second-lead threshold has been relaxed.

Chat gap recovery downloads at most 900 seconds per attempt, with two downloader threads, a five-minute process timeout and a 32 MiB JSON input limit. Oversized windows halve down to thirty seconds before requiring recovery/review. Merged completed intervals and message inserts commit atomically; interruption, new earlier gaps, or overlapping gaps cannot advance an unverified coverage boundary. Message IDs remain idempotent. Completed coverage is checked against the latest gap list. Chat exports use server-side cursors and retain the existing sanitization and message caps instead of loading the whole database archive into memory. EventSub retries database-disconnection bookkeeping failures with bounded backoff rather than letting its thread die.

Settled historical broadcasts refresh metadata every six hours; live/unreconciled broadcasts retain normal discovery frequency. New verified final indexes and alignments retire older related review warnings only after successful validation. The versioned bounded-scoreboard job can resume evidence from the legacy memory-limit failure; genuine ambiguous alignment is not blindly retried or approved.

The local visual aligner no longer rebuilds identical offset groups for every matching frame. Its slope search uses binary-search bounds for the existing 60-to-600-second interval rather than walking the entire remaining video for each anchor. Precise anchors, interval limits, residuals and selected timeline coverage are unchanged. The regression uses 1,000 exact anchors and verifies identical coverage with two median evaluations instead of repeated identical group construction.

Deployment retries are restricted to recognised quota/network failures, the current branch-head release, and two requests per release. Quota failures wait 24 hours; network failures wait ten minutes. Durable request reservations prevent duplicate retries after an uncertain response. Retry requests count against both worker deployment budgets, preserving manual headroom. Incremental publication sleeps until its budget/interval permits another deployment; a newly ready canonical index wakes an incremental batch. A newer verified deployment retires obsolete verification warnings. The production workflow checks the current branch head immediately before deployment and pins the previously observed Vercel CLI 63.1.0. Older workflow revisions without this guard are not automatically rerun.

GitHub retry uses the documented [failed-job rerun API](https://docs.github.com/en/rest/actions/workflow-runs#re-run-failed-jobs-from-a-workflow-run), requiring `SPOILLESS_GITHUB_TOKEN` with Actions write access. Push the workflow update before this recovery path can apply to future GitHub runs. Local worker changes do not update remote workflow files automatically.

The Windows launcher now runs a hidden supervisor. Abnormal exits restart with jittered backoff, capped at eight consecutive short-lived failures; a five-minute stable run resets that count. Normal Stop does not restart the worker, including when the supervisor is between attempts. The launcher verifies supervisor ownership and will not start a duplicate instance while recovery is pending. Container deployments retain `restart: unless-stopped`.

Real provider verification on 2026-10-11: a public FNS VOD yielded all 180 requested one-second samples with a continuous 179-second sample span in 116.656 seconds. The encoded segment cache peaked at 64,241,292 bytes (61.3 MiB), and the observed Python peak working set was 227 MiB. The former large-window failure did not occur. A separate real thirty-second Twitch chat download completed in 2.969 seconds with 104 messages, all inside the requested interval, and a 74,651-byte JSON file. These verify actual media/downloader paths, not complete watch-party publication or a multi-day unattended soak. Deployment rerun failures, cooldowns, budgets and interruptions are verified with fault injection against disposable PostgreSQL; no provider retry was spent just to test recovery.

The actual supervised worker restart confirmed a successful current GitHub deployment, retired twenty obsolete deployment-review warnings, and repeatedly resumed/checkpointed the latest watch-party scoreboard search at its processing slices. Real Start, already-running Start, and Stop were verified across the Windows virtual-environment process chain, including inherited log handles. The latest full Python suite passed 405 tests, followed by six focused status/history checks including one additional generation-retirement regression; all 38 JavaScript checks, Ruff, mypy and compilation passed. The current environment still lacks the explicit GitHub Actions token and Twitch live-user authorization: production automatic deployment reruns and live EventSub chat remain unverified/unavailable until those prerequisites are configured. Public VOD chat retrieval was verified independently.

Unavoidable prerequisites: the machine must stay awake, PostgreSQL must remain available, source footage must still exist, and provider authorization must be valid. Live Twitch chat requires the configured local user authorization; public VOD chat recovery does not replace that authorization. A missing Actions-write token, expired/private/deleted footage, ambiguous match identity, unverified edit boundaries, contradictory canonical evidence, exhausted recovery budgets, and repeated startup crashes still require an explicit human decision. The system never fabricates timestamps or publishes uncertain footage to avoid an alert.

## Processing latency and reliability

The publication objective is 120 minutes from actual match completion. This is a target, not a guaranteed delay timer. Completion, reliable round evidence, correct playback timing and the deployment budget still gate publication. Outcomes are not exposed by the latency report.

Run `python -m pipeline.cli --config indexer/pipeline.rollout.json metrics --broadcast BROADCAST_UUID` with the worker environment to inspect stage attempt time, initial queue delay, source waits, retries, blocking reasons, findings by rule/severity, first-ready time and confirmed provisional/final publication times. Omit `--broadcast` for the recent pipeline. Video-window logs separately report decoded frames, OCR analyses, OCR seconds and elapsed seconds. Repeated unchanged dependency messages are debug-level; their attempts remain measurable in PostgreSQL.

The schedule currently provides completion state, not a verified actual match-end timestamp. `completion_observed_at` records the first observed transition to completed and does not reset on refresh. Historical completed records remain unknown rather than receiving fabricated end times. Reported publication latency uses this explicitly labelled observation time; it can underestimate actual end-to-end latency. Deployment records retain the exact official match versions sent to the site, and only a successfully verified deployment counts as publication. Historical deployments without version membership cannot establish publication times.

Official reconciliation can finish before the entire archive fingerprint pass when the existing strict visual aligner verifies captured live coverage. Remaining fingerprints are background work. An explicit same-source archive-tail recovery job scans footage beyond the last verified captured range with overlap, preserving live checkpoints and reusing saved OCR. Targeted completed-match recovery and validation take precedence over optional upload analysis. Independent Twitch archive capture can run beside official capture/reconciliation, but same-source operations and other broadcast mutations remain serialized.

Long official backfills and separate full-match uploads use adaptive clock sampling with dense verification around round starts. Targeted gap recovery remains dense. Separate uploads require a real 720p source; low-resolution extraction waits for a suitable source instead of producing misleading OCR failures. No canonical confidence or alignment threshold has been lowered. Impossible timestamps, duplicate rounds, backwards numbering, incorrect identity, inconsistent scores and unverified alignment remain publication blockers.

The `canonical-clock-v5` scan stops dense HUD analysis as soon as a round is confirmed. Subsequent checks of that same round use compact scoreboard probes, retained as non-confirming evidence. Dense bursts last six seconds and frozen clocks cannot keep renewing them. After 30 seconds without a usable gameplay clock, break mode probes every six seconds instead of four. A cheap per-frame clock-area appearance check can wake analysis sooner, and a six-second look-back verifies the return to gameplay. Animated backgrounds alone do not force full HUD analysis. There is no fixed-duration break skip. Existing replay-label, introductory-overlay and round-sequence checks remain active. Official archive recovery additionally compares three distinct recent gameplay fingerprints with previously captured footage to reject moving, unlabelled highlights; static images do not establish a replay match.

Archive inputs without a stable format identity reuse a bounded decoder for up to ten minutes of media while retaining the existing 90/120-second database checkpoints. Recovery and upload jobs have separate stream identities, so alternating tasks can resume their own decoder position. Seeking within a task, URL changes, incomplete output and expired streams close the old decoder. Processing slots share at most two idle decoders per media adapter, with two-minute expiry and shutdown cleanup; readers and detector state remain separate. The cache retains pipes, not ten minutes of decoded frames. A restart resumes durable checkpoints rather than the decoder cache.

Resolved non-live YouTube formats share a bounded encoded-video cache across OCR, repair and fingerprint readers. Downloads cover only the requested range in chunks of at most two minutes, with five-second decoding margins; short repairs do not prefetch a full chunk. Existing overlapping ranges are consumed before downloading their uncovered remainder. Original relative packet timestamps, continuous coverage and exact decoded sample positions are verified before use. The cache holds at most four files of 128 MiB each, expires after five minutes and closes on shutdown. Active files cannot be evicted, concurrent readers share one completed download, failed files are discarded, and source/archive revisions or format changes invalidate reuse. Signed URL refreshes do not change the content identity. The first download can cost more than a direct short read; the benefit is avoiding subsequent downloads. Adaptive first-pass backfills and uploads retain streaming decoder reuse when no completed local range covers their window, avoiding cold-cache download latency. They use the encoded cache when that footage is already available.

Official recovery replays compatible saved raw OCR through the current detector instead of decoding the same footage again. Reuse requires the current OCR/detector versions, source revision, archive revision, alias set and direct official archive provenance on the exact sample lattice. Dense repairs rescan unreadable, uncertain and adaptive-only samples; adaptive backfills may reuse their saved non-confirming probes and blanks. Cached dense evidence retains its original capture mode. Untagged legacy samples are rescanned; identical non-accepted observations can receive fresh capture metadata without reducing confidence, while accepted evidence remains unchanged. Fully covered windows require no media resolution, decode, OCR or new image fingerprinting.

Terminal incomplete-map repairs use a stable key scoped to the segment, map and source/archive revisions. Advancing the last detected round no longer replaces the repair job or its durable checkpoint. An extended tail keeps its detector state and recovered evidence. An earlier newly discovered gap gets its own range repair rather than skipping it. Running leases are not mutated, manual-review tasks are not silently reopened, and a new generation does not inherit old progress.

Finding severity distinguishes expected observation noise (info), uncertain observations and noncontradictory upload gaps (warning), invalid canonical invariants (error), and incomplete or unverified canonical evidence (blocking). Errors still block publication. An incomplete upload whose detected sequence is a subset of canonical evidence is recorded as a warning without requiring manual review. A previously verified contradiction remains blocking. Repeated validation waits export only when the immutable index changes; upload validation still exports when its comparison can change publication eligibility.

Baseline measured on 2026-10-10 around 17:33 Europe/Berlin for that day's official broadcast: Twitch archive attempts consumed 9,217 seconds, live capture 4,973 seconds, separate-upload analysis 1,621 seconds, and export attempts 643 seconds. These are summed active-attempt wall times, including I/O, not end-to-end latency or CPU time; concurrent stages must not be summed to infer publication latency. The controlled adaptive test preserves identical round starts, including a missing frame, with 117 analyses instead of 239 (51% fewer). Production latency improvement and the two-hour objective still require subsequent measured completions; the synthetic reduction is not a production speed guarantee.

The v5 real-clip check used cached 720p gameplay, break and introductory-highlight footage from the same broadcast. Confirmed timestamps were identical, and both strategies rejected the highlight footage. OCR calls changed from 50 to 44, 15 to 13 and 54 to 36 respectively. Local analysis wall time was mixed and essentially unchanged overall; these clips establish less repeated analysis, not a measured end-to-end speedup. Decoder reuse and the watch-party short seed have separate regression coverage, including interleaved jobs, exact real FFmpeg timestamps, interrupted output, bounded caches and full-scan fallback. The restarted worker also completed a real 90-second adaptive archive window with 29 OCR calls. Deployment budgets and publication validation are unchanged.

The follow-up reuse benchmark on 2026-10-10 processed the same real 90-second 720p gameplay clip through official recovery and a disposable PostgreSQL database. The first pass took 41.797 seconds with 90 decoded frames and 44 OCR calls; an overlapping pass took 0.281 seconds with no media resolution, decoding or OCR. Confirmed timestamps were identical. A real YouTube test of three overlapping fractional-time windows across full-frame, compact and two-second sampling modes took 16.859 seconds with direct reads versus 12.250 seconds with demand-sized encoded caching (27% less total time). The cold cached read took 10.719 seconds versus 6.437 seconds direct; subsequent cached reads took 0.578 and 0.953 seconds versus 4.250 and 6.172 seconds direct. Decoded timestamps and pixels matched. These measure duplicate-work savings, not full-match first-pass speed or end-to-end publication latency.

The official YouTube broadcast owns the round timeline. A broadcast contains many maps and potentially many matches. Uploads, Twitch, watch parties and schedule providers supply identity, validation or verified recovery evidence. Their timestamps never become published YouTube timestamps without a visual alignment to the official broadcast.

## Existing production path

`auto_publish.py` remains the production publisher during migration. YouTube discovery uses channel feeds or flat yt-dlp playlists; Twitch discovery uses Helix archives and excludes active streams. Official YouTube broadcasts currently supply storyboards. Full-match uploads supply adaptive 540p HUD OCR, with targeted 720p repair for an isolated gap and a full 720p retry for broadly unreliable OCR. Their rounds are translated to the broadcast using `storyboard_align.py`. Twitch/FNS archives are fingerprinted and aligned to the official indexes; `chat_archive.py` downloads VOD chat. `auto_state.json` tracks retries and held dependencies. Generated schema-v2 indexes and `site/catalog.json` are consumed by `site/core.js`, `site/app.js` and the extension. `auto-publish.yml` schedules this work and commits generated files; `deploy-site.yml` deploys the static site to Vercel.

The replacement does not read or mutate `auto_state.json`. Existing catalog entries and historical indexes do not need reprocessing. After an explicit cutover, records marked `canonicalPipeline` are protected from the legacy publisher and its chat alignment writer.

## New flow

1. The coordinator ingests expected matches, discovers official YouTube broadcasts and associates unambiguous day/channel records.
2. Metadata refresh records `discovered`, `scheduled`, `live`, `ended_waiting_archive`, `archive_ready` or `unavailable`. YouTube's actual start and end are preferred. Archive readiness is a separate retryable job which verifies decoding at both ends.
3. Short leased live jobs resolve a fresh HLS URL, sample compact HUD/replay regions and a small fingerprint thumbnail, then checkpoint each media segment. HLS program-date-time plus the actual broadcast start establishes media time. Missing clock anchors are held for recovery; no arrival-time or constant-offset guess is made. A worker restart resumes persisted detector agreement and the source checkpoint.
4. The detector retains candidates, including rejected evidence. It requires three decreasing gameplay clocks that agree with elapsed media time. Frozen clocks, detected buy phases, replays, impossible scores and duplicate observations cannot finalize a round. A score reset and a coherent prior map are required for map resets.
5. Segmentation considers coherent round/map sequences, score resets and a confirmed change of team identity. Team names require agreement in at least two detector frames. A gap or reset alone does not split a series. Schedule order checks identity; schedule times never set video boundaries. Ambiguous segments stay `needs_review`; other matches continue independently.
6. Completed expected matches get their own validation jobs and immutable index versions. A map tail whose captured starting scores cannot produce a legal map-ending result is incomplete, including overtime tails. Known following-map starts bound targeted tail recovery. Pending canonical capture-gap jobs block publication even when the segment is closed or the gap was discovered before match assignment. Live publication verifies continuous HLS coverage and embedded video presentation timestamps at the beginning, middle and end of the indexed range. Those anchors translate the internal program-date-time clock to the YouTube playback clock; actual broadcast start metadata alone is not the playback origin. Inconsistent anchors or HLS discontinuities require archive reconciliation/review. The measured conversion applies only to provisional live indexes, preserves OCR/checkpoints, and leaves the website's five-second lead unchanged. Final archive reconciliation operates on the original captured evidence and does not apply the live conversion again. With verified coverage and clock anchors, a valid match can become `provisional`. Otherwise its validated index is retained in `validating` until the archive is seekable; publication does not repeat OCR. Release snapshots explicitly withhold invalidated match indexes. Installation removes only the affected canonical listing, keeps an ownership/version record under `withheld`, rejects stale re-publication, and preserves unrelated historical entries. The legacy publisher respects that ownership while recovery is pending.
7. Archive reconciliation fingerprints the official archive at two-second intervals, resumes its fingerprint checkpoint after failure, and reuses the existing segmented visual aligner. Only verified anchor ranges are mapped; ambiguous edit boundaries are held for review. If broadcast-wide alignment is uncertain, independent segment reconciliation jobs can still finalize verified matches. Reconciliation uses fingerprints, not another full OCR pass. Each affected match finalizes independently.
8. Missing ranges request direct 720p official-archive OCR. If it finds no coherent rounds, recovery tries registered full-match uploads and then official Twitch archives with verified piecewise mapping. Only missing lower-priority evidence can supplement the canonical sequence. Targeted live gaps first use retained official live DVR at 720p, in at most 18 HLS segments per attempt. Recovery keeps its own detector/sequence checkpoints in the job payload and preserves the main live-capture detector/checkpoint. Unavailable DVR ranges wait for the archive. Exhausted or ambiguous recovery becomes `needs_review`.

With no captured live rounds, the finalized official archive can be indexed directly. Its identity mapping is an explicit same-source archive identity, not an inferred cross-video offset. Direct OCR begins immediately; archive fingerprints run as separate background work. During that backfill, a match is publishable only after a confirmed following match boundary or completion of the archive scan. Captured live rounds with insufficient fingerprints require review rather than silently adopting the archive clock.

## Database and jobs

When recovery obtains a readable HUD observation at a previously unreadable sample time, checkpointing retains the improved supporting observation even before its round is confirmed. Already accepted evidence is never overwritten by a rejected observation. This lets canonical replay reproduce the recovered round's multi-frame clock agreement instead of replaying stale unreadable samples.

Official archive OCR recovery requires an actual source resolution of at least 720p. When the configured Android client supplies only a lower-resolution stream, extraction tries the public client instead; if no adequate stream is available, recovery waits rather than silently upscaling blurry footage. Quality-constrained media results have isolated cache keys. Targeted gap recovery checks that the missing round identities have actually appeared in verified canonical evidence before reporting success; detecting an already-known neighboring round is insufficient. Full archive backfill retains its existing bounded checkpoint behavior.

Run migrations before starting work. Files in `migrations/` are ordered, transactional, checksummed and protected by an advisory lock. Do not edit an applied migration.

The `pipeline` schema has broadcasts, expected matches, sources, raw round candidates, fingerprints, detected segments, versioned match indexes, alignments, chat archives/messages, source events, jobs and attempts. Foreign keys, uniqueness constraints and canonical-source triggers protect ownership and generation. JSONB stores evidence and immutable round sequences, not the primary job lifecycle.

Jobs are `queued`, `running`, `waiting_source`, `retryable`, `succeeded`, `needs_review` or `unsupported`. Claiming uses PostgreSQL `FOR UPDATE SKIP LOCKED`, with aging so completed-match work is not starved by live capture. Lease tokens fence attempts; expired leases create a recorded expired attempt and permit recovery. Heartbeats renew leases. Every durable processing write checks the current lease and broadcast generation. Index publication also checks source, archive and segment revisions. Retrying successful work does not create duplicate evidence or index versions. Temporary failures use bounded exponential backoff from 30 seconds to one hour; after twelve consecutive failures the job needs review. Successful recurring jobs reset the failure counter.

`reconcile --new-revision` advances the archive revision and generation, fencing older work. Only use it when a changed archive needs new verification. It fingerprints again but retains detector evidence. Old generations are preserved in the database; new results require new validation.

Live capture is prioritized above archive reconciliation, and canonical recovery is prioritized above optional Twitch archive/alignment work. Canonical reconciliation, fingerprint and recovery jobs become eligible immediately after a bounded checkpoint; their yield does not create a delay window for a long optional job. Twitch alignment discovery schedules each source/canonical-revision/five-minute capture bucket only once, including after success. A new bucket or canonical revision requests a fresh alignment.

Upload validation is not claimable until its assigned canonical segment exists. Full-match validation and direct official recovery process at most 90 media seconds per turn; archive fingerprinting processes at most 120 media seconds. They checkpoint, release the lease and requeue without consuming failure retries. Attempts record `yielded` for these successful partial turns. Canonical discovery, live capture and other matches can run between windows. Resuming upload validation uses its saved OCR rather than starting from the beginning.

## Configuration and deployment

### Windows launcher and operator status

Double-click `Start Worker.cmd` in the repository root. The launcher uses `.venv-indexer`, `indexer/pipeline.rollout.json`, publish mode and the existing local PostgreSQL cluster at port 55439. An inherited `DATABASE_URL` is preserved; managed databases are not started locally. The existing local cluster is started in a separate hidden process so closing the launcher does not stop it. Dependencies and the cluster must already be installed. Startup errors name the configuration or log file requiring attention.

`indexer/launch-worker.ps1 -Shadow` selects shadow mode; `-Config PATH` selects another configuration; `-NoBrowser` leaves the browser closed. Rerunning the launcher reopens the status page for its existing worker without launching a duplicate. Stop a manually started or older worker with Ctrl+C once before using the launcher. `Stop Worker.cmd` and the status page's Stop worker button request graceful shutdown without stopping PostgreSQL. Logs and launcher state are stored under ignored `indexer/data/`; the local state includes an authentication token and should not be shared.

The page at `http://127.0.0.1:8767/` polls the authenticated `/operator-status` endpoint. The launcher supplies its token through a URL fragment, which the page removes immediately. Reopening the page with the launcher restores access. Match labels show scheduled team pairings, event and match order; scores, rounds, timings, findings and raw processing errors are omitted from the operator response. The existing authenticated `/status` diagnostic endpoint is unchanged. The page separates match preparation from website publication and explains publication waits, source updates, review flags and worker publication budgets. Processing counts and update history are expandable. A GitHub push is not shown as a confirmed live deployment. Vercel's precise reset time remains unknown; failed verification is shown as unconfirmed. If the worker stops, an already open page marks its last status as stale; reopen it through the launcher after restarting.

Expand a match's review dropdown and choose `Review task` for source links, task-specific guidance and a confirmation checkbox before retrying. `Copy review details` copies a spoiler-safe issue report with the task identifier. Review state stays open across status refreshes. Authenticated `POST /retry-job?id=JOB_UUID` accepts only current-generation `needs_review` tasks, rejects changed or leased tasks, and resets the existing retry counter without changing evidence, segment state or validation rules. It uses the same retry implementation as the CLI. Source videos may contain spoilers; opening them is an explicit action. A retry queues checks again, not an approval. Issues requiring source registration, evidence repair or configuration changes still need those corrections before retrying.

Install Python 3.12, Node 22 or newer, and `indexer/requirements-worker.txt`. The Docker image includes Node 24. yt-dlp's pinned `default` dependencies include the matching EJS challenge solver; do not install yt-dlp without those extras. PostgreSQL 17 is the deployment/test target. No Redis or queue service is required.

Provider failures leave durable schedules intact and indexing continues with reduced identity metadata. A schema change raises a provider warning. The provider interface is `matches() -> list[dict]`. There is no VLR scraper in this implementation.

Schedule ingestion finds existing matches by provider and external ID before considering their listed position. A shortened provider response cannot renumber a stored match or overwrite another provider ID occupying its slot. Conflicting new automatic identities log `schedule_identity_conflict` and leave the stored record intact. Explicit manual schedule overrides retain their existing slot behavior.

An operator-verified live identity can be protected with `manual_override.live_identity_repair`. Automatic ingestion preserves its teams and aliases while accepting completion updates only from the same provider and external ID. The running worker must restart to load this ingestion behavior; its older importer skips that protected record entirely. The existing `review-segment --match ... --reason ...` command can associate saved rounds using verified broadcast/HUD identity without changing timestamps or waiving sequence findings.

A broadcast marked unavailable with `metadata.manual_exclusion` is omitted from routine discovery refresh and the updated refresh handler ignores queued refreshes for it. Excluded vertical companion streams retain their saved evidence. Configure the channel title exclusion to reject `VERTICAL` and `#shorts` before future discovery.

## Twitch and chat

## Operations

The `vct-clock-ocr-v10` HUD reader retries a low-confidence gameplay clock using two padded crops. Both crops must agree with the original timer and independently meet the existing confidence threshold. Multi-frame round confirmation is unchanged. Recovery range keys include the HUD reader version, so a parser upgrade schedules new bounded recovery work without clearing completed attempts or source checkpoints. An incomplete final map now requests recovery from its last detected round through the available official archive fingerprint coverage, including a tail missed when live capture stopped early.

Full-match sequence validation checks the expected best-of format. A source that detects too few maps, but has coherent detected sequences entirely contained in a complete canonical index, is recorded as `source_incomplete`. Malformed upload OCR is recorded as `source_needs_review`; its raw sequence differences cannot establish a verified contradiction. Both states retain source findings and diagnostics without vetoing a separately complete validated canonical index. Missing canonical rounds and verified current-segment contradictions still block release; repeated source errors cannot clear a known verified contradiction. Upload checks include the HUD reader version so existing comparisons re-evaluate after restart using stored observations.

Periodic segmentation preserves the stored full-match comparison instead of erasing its classification. Unchanged segmentation does not change the segment revision or create another validation job. When a comparison was already erased by an older worker, retry the existing upload-validation job after restarting; its stored OCR is reused.

Reconciliation uses the versioned `storyboard-v5` aligner. Imprecise visual matches are removed before the two-second residual check; each section must retain at least five precise anchors spanning 60 seconds, and global beginning/middle/end coverage remains required. Rejected edge anchors cannot extend publishable timestamp coverage. Refresh requeues the existing failed reconciliation job when the aligner version changes, retaining saved source checkpoints and archive fingerprints. Restarting the worker applies the upgrade without a database reset or repeating completed fingerprint extraction.

Storyboard and local secondary-source matching predecode reference hashes and compare their bits using NumPy arrays. They select the best two distances without sorting every reference frame. Exact distances, ambiguity rejection, residual limits and anchor coverage rules are unchanged; nonstandard legacy hash widths retain scalar comparison. Restart the worker to load this optimization. Existing indexes and reconciliation revisions do not require rebuilding.

Completed automatic recovery ranges are not reopened by repeated segmentation; their saved progress and attempts remain intact. A new broadcast generation or an explicit `reprocess-range` request can run recovery again. Upload sequence gaps wait while relevant canonical coverage or targeted recovery is pending, then recheck saved upload OCR. Exhausted recovery and genuine sequence contradictions still require review. Segmentation includes current coverage state in upload-validation payloads so existing checks requeue when their dependencies change, without duplicate jobs or resetting source checkpoints.

Ready segmentation, validation, finalization and export jobs that have waited at least 60 seconds take precedence at the next job claim, allowing completed matches to advance between archive chunks. This does not interrupt running media work. Temporary access failures in fallback recovery retain bounded source retries instead of being classified immediately as exhausted visual evidence.

Validation success, waits and failures schedule a fresh release snapshot. A missing broadcast start withholds only the affected match and logs its IDs; other safe matches still export. These changes prepare release artifacts automatically; installation and website deployment remain the separate cutover steps described above.

YouTube discovery is a durable `discover_youtube` job per configured channel, retaining separate broadcast and full-match routes. RSS is preferred; an unavailable or malformed feed falls back to lightweight yt-dlp `/streams` and `/videos` listings with the same title filters and 30-entry limit. Live/upcoming broadcasts remain discoverable. RSS failures log one warning and suppress RSS requests for 30 minutes while tab discovery continues. Both processing slots share this discovery adapter. If tab discovery also fails, the job enters `waiting_source`, with persisted exponential backoff from 30 seconds to one hour. The existing 12-attempt bound then requires `retry-job` after reviewing availability/configuration. Coordinator ticks retain the retry deadline and continue scheduling existing broadcasts. Successful routes retain their work when another route fails. Known broadcasts/uploads are not re-associated, and stable discovery/association job keys prevent duplicate rows. `schedule_routes`, shadow mode, archive checkpoints and source revisions are unaffected.

Keep PostgreSQL running independently of the worker. Database connections default to a five-second timeout; an explicit `connect_timeout` in `DATABASE_URL` takes precedence. After a database outage, workers reconnect through their existing polling loop, reclaim expired leases and resume durable checkpoints. The `inspect-broadcast` CLI below verifies database connectivity. For the local Windows test cluster, only if the server has stopped, start it with `& .\indexer\data\pg-test\bin\pg_ctl.exe start -D indexer/data/pg-test/cluster -o "-h 127.0.0.1 -p 55439" -l indexer/data/pg-test/test.log`. yt-dlp plugins initialize before discovery and processing threads start, preventing concurrent provider registration.

The worker runs two processing slots by default (`"processing_slots": 2`); set this to `1` for a smaller host. Slots have independent media analysis/OCR instances and share the durable job queue. Different broadcasts can process concurrently; jobs sharing a broadcast or source are serialized at claim time. A short PostgreSQL advisory transaction lock prevents simultaneous claims from bypassing this check. Catalog exports already serialize through the publication lock. Discovery and EventSub run once per worker process. `--once` still processes one job. Stop and restart the worker to apply configuration or code changes; shutdown waits for processing slots to exit and saved checkpoints survive restart.

Archive OCR, secondary recovery, upload validation and archive fingerprint chunks reuse resolved YouTube URLs within each processing slot for up to five minutes. The cache separates video IDs, requested heights and authentication settings, holds at most 128 entries, and expires signed URLs three minutes before their declared expiry. Returned headers are independent copies. Live media resolution, archive readiness and reconciliation continue to probe fresh metadata. Source waits invalidate the processing slot's cache before retry; secondary YouTube source waits invalidate that video's entries even when another fallback is attempted. The cache is memory-only and never changes checkpoints, database state or canonical timestamps. Restarting requires no configuration change and starts with an empty cache.

Official archive OCR also saves two-second archive fingerprints from its decoded frames under the current archive revision. Full-frame hashes use the same 320×180 normalization as the standalone fingerprint pass. The fingerprint job fills the earliest missing range on the two-second grid, at most 120 seconds per claim, and skips ranges already covered by OCR or prior fingerprint jobs. A later stored anchor cannot hide an earlier gap. Existing fingerprints are retained, and restart resumes missing coverage without rerunning completed OCR. `archive_fingerprint_time` reports the highest stored fingerprint time, not proof that all earlier ranges are covered. No new migration or configuration is required.

### Intro highlight filtering

The `canonical-clock-v4` detector retains pending agreement across repeated clock readings less than one second apart. Repeated readings never count toward confirmation; three decreasing, consistent clock observations are still required. During archive segmentation, verified live detections mapped through reconciliation provide preceding map and round context for isolated archive recovery windows. This lets stored recovery observations repair gaps without fetching media again or assuming that unsampled intervals contain map resets.

`canonical-clock-v3` distinguishes pre-match highlight footage from gameplay using a high-confidence three-part countdown plus a matchup label in the top-left overlay. A gameplay clock alone, a matchup label alone or low-confidence overlay text cannot trigger this filter. Intro observations retain raw context evidence and a rejection reason. Stored diagnostics for older accepted candidates are checked once during segmentation; the context result is persisted on each candidate, and the corresponding countdown interval excludes intro observations during stored OCR replay. Original accepted flags and OCR remain historical evidence, rather than being erased.

After restarting with the same configuration, periodic segmentation automatically applies this classification, rebuilds map numbering and requeues validation only for changed segments. Saved archive positions are retained; detector state upgrades through the existing stored OCR replay path. No one-time recovery command or database migration is necessary. Missing diagnostics or ambiguous overlays retain conservative review behavior. A low round count does not establish a sampling failure: on `ynKvUYpu1Qw`, stored observations and two spot checks show pre-match content before the first coherent pistol round at 5438 seconds. Recovery must not invent rounds in that interval.
